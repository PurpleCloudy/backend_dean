# БД «Деканат» — PostgreSQL

База данных для проекта «Интеллектуальный агент для автоматизации процессов деканата» (МГТУ «СТАНКИН»).

**56 таблиц · 312 атрибутов · 83 внешних ключа · 27 представлений · НФБК · 184 автотеста**

Тестовые данные — Институт информационных технологий: 22 группы с шифрами по правилам СТАНКИНа (ИДБ-23-11 … ИДБ-26-15, ИДМ-25-06, ИДМ-26-06), 508 студентов, история учёбы за три года и полное расписание текущего семестра.

## Запуск

Одной командой (от пользователя с правом создавать БД и роли, например `postgres`), Linux / macOS:

```bash
./rebuild.sh     # пересоздаёт БД deanery, выполняет все скрипты и автотесты
```

На Windows — `rebuild.bat` (папка `bin` PostgreSQL должна быть в `PATH`). При ручном запуске `psql` на Windows сначала выполните `set PGCLIENTENCODING=UTF8`, иначе русский текст из файлов исказится.

Или по шагам:

```bash
createdb deanery
psql -d deanery -f 01_schema.sql            # таблицы, ключи, ограничения, индексы, описания
psql -d deanery -f 02_views_functions.sql   # представления, триггеры, аудит, процедуры
psql -d deanery -f 03_seed.sql              # тестовые данные (сгенерированы generate_seed.py)
psql -d deanery -f 04_crud_examples.sql     # демонстрация CRUD (откатывается ROLLBACK)
psql -d deanery -f 05_roles_security.sql    # роли и права доступа
psql -d deanery -f 06_tests.sql             # автотесты правил (откатываются ROLLBACK)
psql -d deanery -f 07_fd_scan.sql           # необязательно: поиск скрытых функциональных зависимостей
```

Все объекты лежат в схеме `deanery`; в сессии выполните `SET search_path TO deanery, public;`.
Нужно расширение `btree_gist` (входит в стандартную поставку PostgreSQL). Проверено на PostgreSQL 16 (подойдёт 14+).

## Шифры групп по правилам МГТУ «СТАНКИН»

Группы называются так, как в расписаниях и учебных планах СТАНКИНа:

```
ИДБ-24-11
│││  │  └─ номер группы в наборе института (11, 12, …)
│││  └──── год набора (2024)
││└─────── уровень: Б — бакалавриат, М — магистратура, С — специалитет
│└──────── форма обучения: Д — дневная (очная)
└───────── институт: И — Институт информационных технологий
```

Допускается суффикс в скобках, как у реальных групп: `ИДМ-24-03(ИГ)`.

Буквы хранятся в справочниках (`institute.group_letter`, `study_form.group_letter`, `education_level.group_letter`), а не зашиты в код. Шифр — официальный идентификатор группы, поэтому он хранится, а триггер `group_name_check` сверяет его с учебным планом: буквы и год должны совпадать, иначе база подскажет правильное начало (`ожидается «ИДБ-25-NN»`). Функция `fn_group_prefix(curriculum_id)` возвращает это начало — агент может предлагать шифр новой группы.

В тестовых данных у каждого набора бакалавриата пять групп: 11 и 12 — «Программная инженерия» (09.03.04), 13 — «Прикладная информатика» (09.03.03), 14 и 15 — «Информационные системы и технологии» (09.03.02). Магистратура — `ИДМ-25-06`, `ИДМ-26-06` (09.04.04).

## Успеваемость: модульно-рейтинговая система

Все результаты — модули, зачёты, экзамены, практика, курсовые и ВКР — ставятся в баллах по одной шкале (таблица `score_band`, границы меняются в одном месте):

| Баллы | Оценка |
|---|---|
| 25–34 | 3, удовлетворительно |
| 35–44 | 4, хорошо |
| 45–54 | 5, отлично |

Меньше 25 баллы не выставляются: ставится «не аттестован» (`points` пусто) или «неявка» (`is_absent`). Для зачёта 25 и больше — «зачтено». Оценка по баллам не хранится, а вычисляется функцией `fn_mark()`.

У дисциплины два промежуточных модуля (`curriculum_item.module_count`), у практики, курсовой и ВКР модулей нет, но итоговая оценка в той же шкале. На каждый этап — модуль 1, модуль 2, итоговый контроль — оформляется своя ведомость (`grade_sheet.stage`), со своими пересдачами.

Отчёт по студенту:

```sql
SELECT semester, discipline, module_1, module_2, credit AS "зачёт", exam AS "экзамен", final_result
FROM v_performance WHERE student LIKE 'Иванов%' ORDER BY semester, discipline;
```

```
 сем |   дисциплина                         | м1 | м2 | зачёт | экзамен |  итог
   4 | Базы данных                          | 48 | 51 | —     | 52      | Отлично
   4 | Иностранный язык                     | 50 | 49 | 50    | —       | Зачтено
   6 | Производственная практика            | —  | —  | 50    | —       | Отлично
   7 | Системы искусственного интеллекта    |    |    | —     |         |
```

«—» — такого контроля у дисциплины нет; пусто — ещё не выставлено; «н/а» — не аттестован; «неявка». После пересдачи показывается последний результат.

Результаты сопоставляются по дисциплине и семестру, а не по строке конкретного учебного плана. Поэтому если студента перевели в группу другого года набора (после академа или восстановления), его прежние результаты по той же дисциплине того же семестра видны и в новой группе.

## Расписание на семестр

Семестры (`academic_term`) задают даты занятий и сессии, от начала семестра считаются учебные недели (1-я — нечётная). Праздники (`holiday`) исключаются из календаря. Занятие в сетке идёт каждую неделю, только по нечётным или только по чётным; если оно идёт не весь семестр, период ограничивается (`valid_from` / `valid_to`).

```sql
-- расписание группы на любой период семестра
SELECT lesson_date, weekday_name, week, pair_number, start_time, discipline, lesson_type, teacher, classroom
FROM v_schedule_calendar WHERE group_name = 'ИДБ-23-11' ORDER BY lesson_date, pair_number;

-- где сетка не добирает часов до учебного плана
SELECT * FROM v_schedule_hours WHERE scheduled_hours < planned_hours;
```

В тестовых данных осенний семестр 2026/27 расписан полностью для всех 22 групп: 223 строки недельной сетки, около 9 пар в неделю у бакалавров, лекции общих дисциплин читаются потоком на все пять групп набора. Лекции «Управления программными проектами» идут только первые 8 недель — пример занятия на часть семестра. По каждому занятию сетка покрывает не меньше 88 % часов учебного плана (`v_schedule_hours`).

## Операции (CREATE / UPDATE / DELETE)

Обычный CRUD — `INSERT / UPDATE / DELETE` по таблицам; примеры для каждой сущности в `04_crud_examples.sql`.
Составные операции деканата — процедуры, каждая выполняется одной транзакцией и сама оформляет приказ. Статус, группу и дату зачисления студента меняют **только** они: у ролей деканата и агента нет права на прямой `UPDATE` этих полей.

| Операция | Вызов (последний параметр необязателен — дата вступления в силу, по умолчанию сегодня) |
|---|---|
| Зачисление | `SELECT fn_enroll_student('Фамилия','Имя','Отчество','M','2008-01-01','e@mail','+7…','ИДБ-26-13','Бюджет','№ зачётки','№ приказа',CURRENT_DATE, подписант [, дата начала обучения])` |
| Перевод | `CALL sp_transfer_student(id, 'группа', '№ приказа', подписант [, дата])` |
| Отчисление | `CALL sp_expel_student(id, '№ приказа', 'причина', подписант [, дата])` |
| Академический отпуск | `CALL sp_grant_academic_leave(id, 'причина', начало, конец, '№ приказа', подписант)` |
| Выход из отпуска | `CALL sp_return_from_leave(id, '№ приказа', подписант [, дата выхода [, 'новая группа']])` |
| Восстановление | `CALL sp_reinstate_student(id, 'группа', '№ приказа', подписант [, дата])` |
| Отмена запланированного приказа | `CALL sp_cancel_scheduled_order('№ приказа', id)` |
| Исполнение наступивших приказов | `SELECT fn_apply_due_orders()` — раз в сутки (см. ниже) |
| Заявка на исправление оценки в закрытой ведомости | `SELECT fn_request_grade_correction('№ ведомости', '№ зачётки', баллы, неявка, 'основание')` |
| Решение по заявке | `CALL sp_decide_grade_correction(id заявки, TRUE/FALSE, 'комментарий')` |

Каждая процедура сначала проверяет статус студента: нельзя отчислить отчисленного, перевести его или отправить в академ, перевести в ту же или в архивную группу, восстановить того, кто не отчислен.

### Приказы вступают в силу в свою дату

Приказ записывается сразу, а статус, группа и стипендии меняются **в день вступления в силу**, не раньше:

- если дата сегодняшняя (или для отпуска — начало уже наступило), процедура исполняет приказ сразу;
- если дата в будущем, приказ попадает в `v_pending_orders` (`order_student.applied_at` пусто), а студент пока остаётся в прежнем статусе и группе;
- наступившие приказы исполняет `fn_apply_due_orders()`. Процедуры вызывают её сами для своего студента, а для всех остальных её нужно запускать раз в сутки — планировщиком бэкенда или `pg_cron`:

```sql
SELECT cron.schedule('deanery-orders', '5 0 * * *', 'SELECT deanery.fn_apply_due_orders()');  -- если есть pg_cron
```

  Если какой-то приказ исполнить не удалось, остальные всё равно исполняются, а этот остаётся в `v_pending_orders` с предупреждением в журнале сервера;
- стипендия при отчислении прекращается по дате вступления приказа в силу, при академе — по дате начала отпуска, даже если ежедневный запуск прошёл позже;
- у студента не больше одного запланированного приказа (уникальный индекс): вторая операция до исполнения первой отклоняется с подсказкой, как отменить первую;
- приказ задним числом не оформляется; исполненный приказ нельзя отменить, удалить из истории или переписать; тип, институт и даты приказа со студентами менять нельзя;
- отметку об исполнении (`applied_at`) ставит только `fn_apply_due_orders` — у ролей нет права записывать этот столбец.

Зачисление с будущей датой начала обучения даёт статус «Зачислен»: студент уже в базе, но оценки и посещаемость ему ставить нельзя, пока он не станет «Обучается».

### Досрочный выход из академа освобождает остаток периода

У отпуска есть плановое окончание (`end_date`) и фактическое — `fn_leave_actual_end()`: день перед выходом по приказу о выходе. Пересечение отпусков одного студента проверяется **по фактическому периоду**, поэтому после досрочного выхода в оставшейся части планового интервала можно оформить новый отпуск. Выход можно назначить и на будущую дату (например, к началу весеннего семестра): студент до этого дня остаётся в отпуске, а остаток периода освобождается сразу. Если запланированный выход отменить, отпуск снова длится до планового окончания (если это не создаёт пересечения).

### Приказ проверяется по студенту, типу и институту

Любая ссылка на приказ — отпуск, выход из отпуска, стипендия, направление на практику, тема ВКР — принимается, только если приказ нужного типа, студент включён в этот приказ и приказ издан институтом, где учится студент. Само включение студента в приказ (`order_student`) проверяет институт его группы (при восстановлении — новой группы), что новая группа из того же института и не в архиве, а для перевода и восстановления — что она указана. Приказ подписывает директор **этого** института или его заместитель.

### Исправление оценки в закрытой ведомости

Напрямую оценку в закрытой ведомости не изменить. Исправление — отдельная подтверждённая операция:

1. **Заявка** — `fn_request_grade_correction(...)`: подаёт сотрудник деканата, агент или преподаватель (только по своей ведомости). В заявке фиксируются старое и новое значение и основание.
2. **Решение** — `sp_decide_grade_correction(...)`: принимает директор или заместитель директора института группы, **не автор заявки**. При одобрении оценка меняется в той же транзакции; при отказе нужен комментарий.
3. **Аудит**: в журнал попадают подача, решение и само изменение оценки с именем того, кто подтвердил.

Заявку нельзя подать, если оценка уже изменилась, если после этой попытки была пересдача (исправлять нужно последнюю), если новые баллы вне шкалы; по одной оценке в работе может быть только одна заявка; рассмотренную заявку нельзя рассмотреть повторно.

```sql
SELECT set_config('app.user_id', '5', TRUE);   -- преподаватель
SELECT fn_request_grade_correction('ИДБ-23-11/5/24/И', '23-1102', 40, FALSE, 'Не учтён доклад на семинаре') AS id \gset
SELECT set_config('app.user_id', '1', TRUE);   -- директор института
CALL sp_decide_grade_correction(:id, TRUE, 'Подтверждаю');   -- :id — номер заявки из psql (\gset)
SELECT * FROM v_grade_corrections;
```

## Правила целостности

Полный перечень всех правил, которые проверяет база, — в отдельном файле `INTEGRITY_RULES.md`. Ниже — кратко.

Простые правила заданы через `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`, `NOT NULL`. Правила, которые связывают несколько таблиц, проверяют триггеры и ограничения `EXCLUDE`:

- **Баллы.** Только в пределах шкалы (25–54); баллы и неявка одновременно невозможны; закрытую ведомость напрямую менять нельзя — только по заявке, подтверждённой директором или заместителем; студент — из группы ведомости (в ведомость пересдачи можно внести студента с долгом по этой дисциплине, даже если его перевели).
- **Учебный план.** Ведомость и учебное поручение — только по дисциплине из плана этой группы. Практика — только по строке плана вида «практика», тема — только за курсовой или ВКР, и всё из плана самого студента.
- **Посещаемость.** Студент из группы занятия и сейчас обучается; дата — в период занятия, в нужный день недели, с учётом чётности недели, не в праздник и не в будущем.
- **Староста** — обучающийся студент своей группы. При переводе, отчислении или уходе в академ снимается автоматически.
- **Сотрудники.** Преподаватель — только на преподавательской должности, сотрудник деканата — на административной или вспомогательной, одновременно обоими быть нельзя. Заведующий кафедрой — преподаватель этой кафедры (проверка отложена до конца транзакции). Директор института — работающий сотрудник на административной должности.
- **Шифр группы** — по правилам СТАНКИНа: формат `ААА-ГГ-NN`, буквы института, формы и уровня и год набора совпадают с учебным планом группы.
- **Периоды.** Одинаковые стипендии не пересекаются (`EXCLUDE USING gist`); академические отпуска одного студента не пересекаются по фактическому периоду (триггер с блокировкой по студенту); отпуск не длиннее 2 лет.
- **Приказы.** Ссылка на приказ — только на приказ нужного типа, своего института, в который включён этот студент; изменения по приказу — в дату вступления в силу.

### Защита от неверного ввода и действий

- **Текст.** Во всех текстовых полях запрещены пустые строки, строки из пробелов и пробелы по краям. Email, email родителей и логины уникальны без учёта регистра.
- **Даты.** Человеку не меньше 14 лет, дата рождения не в будущем; зачисление не раньше 14 лет, приём на работу — не раньше 16; посещаемость нельзя отметить на будущую дату; семестр не больше срока обучения по плану.
- **Ведомости.** На каждый этап дисциплины (модуль 1, модуль 2, итог) у группы одна действующая основная ведомость; модульную ведомость нельзя создать для практики, курсовой и ВКР, и им нельзя назначить модули в плане. Закрытую или отменённую ведомость нельзя открыть снова — оформляется новая. Основную ведомость можно закрыть, только когда оценки (включая «неявку») есть у всех обучающихся студентов группы; пустую пересдачу закрыть нельзя.
- **Оценки.** Только обучающимся (не в академе, не отчисленным). В пересдачу можно внести только того, кто по этому этапу дисциплины ещё не аттестован.
- **Сотрудники.** Уволенного нельзя назначить преподавателем, экзаменатором, руководителем, куратором, заведующим. Нельзя уволить директора, заведующего или куратора, пока на его место никого не назначили. Приказы подписывает только работающий руководитель института, который их издаёт.
- **Стипендии.** Только обучающимся; государственные — только бюджетникам (признак `budget_only` у вида стипендии). На время академа выплата прекращается автоматически.
- **Прочее.** Группу с обучающимися нельзя отправить в архив, а в архивную группу нельзя зачислить или перевести. Выданную или отклонённую справку нельзя вернуть в работу.
- **История не удаляется каскадом.** Внешние ключи на студентов, приказы, ведомости и занятия — `ON DELETE RESTRICT`: случайный `DELETE` студента, приказа или занятия с посещаемостью будет отклонён, а не сотрёт оценки и приказы.

Проверки, которым нужны скрытые от роли данные (например, дата рождения), выполняются как `SECURITY DEFINER`, поэтому работают одинаково для деканата и для агента.

### Расписание

Два занятия пересекаются, если совпадают день и пара, пересекаются периоды действия и чётность недели («каждая» пересекается и с чётной, и с нечётной). Тогда запрещено:

- одна **аудитория** или один **преподаватель** — кроме лекционного потока (один преподаватель читает одну лекцию нескольким группам в одной аудитории);
- одна **группа** — кроме занятий разных подгрупп;
- суммарная численность групп больше **вместимости** аудитории.

Проверка срабатывает и при изменении учебного поручения (например, при замене преподавателя). Параллельные вставки в одну и ту же пару сериализуются рекомендательной блокировкой, чтобы две транзакции одновременно не заняли одно время.

## Автотесты

`06_tests.sql` — 184 проверки: для каждого правила база должна отвергнуть неверные данные (и по нужной причине — тест сверяет текст ошибки) и принять верные (лекционный поток, занятия по чётным/нечётным неделям, пересдача переведённого студента, восстановление, выход из академа, отчисление кандидата агентом, приказ на будущую дату и его исполнение в срок, новый отпуск в освободившемся после досрочного выхода интервале, исправление закрытой ведомости с подтверждением директора), а у каждой роли должны быть ровно заявленные права. Тесты ищут данные по зачёткам, шифрам групп и дисциплинам, а не по внутренним номерам записей. Все изменения откатываются. Если какое-то правило не сработает, скрипт остановится с ошибкой «✗ …».

## Нормализация: НФБК (нормальная форма Бойса — Кодда)

- **1НФ** — все атрибуты атомарны: ФИО разбито на три поля, паспорт — серия и номер, ФИО и должность руководителя практики — в отдельных полях, изменения в журнале хранятся по одному полю в строке, нет списков в одной ячейке, у каждой таблицы есть первичный ключ.
- **2НФ** — нет зависимостей от части ключа. Составные ключи есть только у связок M:N (`order_student`, `student_contact`), у детализации журнала и у альтернативных ключей (`UNIQUE`).
  - Направление и профиль разделены: `specialty` (код ФГОС → название, уровень) и `study_program` (профиль, выпускающая кафедра). В одной таблице с ключом «код + профиль» название зависело бы только от кода.
- **3НФ** — нет транзитивных зависимостей:
  - персональные данные хранятся один раз в `person`, а студент/сотрудник ссылаются на неё (супертип/подтипы);
  - группа ссылается на учебный план, а программа, форма обучения и год набора берутся оттуда;
  - институт преподавателя определяется через кафедру, поэтому в `teacher` нет `institute_id`;
  - **курс и семестр не хранятся**, а вычисляются функциями `fn_course()` / `fn_semester()`;
  - сумма стипендии хранится в виде стипендии, а не у каждого студента;
  - операция и целевая таблица агента определяются намерением и хранятся в `agent_intent`;
  - вид работы (курсовая или ВКР) определяется дисциплиной, а дата выхода из академа — приказом о выходе, поэтому отдельно они не хранятся; **фактическое окончание отпуска** при досрочном выходе тоже не хранится, а вычисляется `fn_leave_actual_end()` — поэтому пересечение отпусков проверяет триггер, а не `EXCLUDE` (ему понадобилась бы копия даты выхода в `academic_leave`, то есть транзитивная зависимость);
  - **ЗЕТ не хранится**: 1 ЗЕТ = 36 часов, трудоёмкость вычисляется функцией `fn_credits()` (представление `v_curriculum`);
  - **дата оценки не хранится**: у всех оценок ведомости одна дата — дата экзамена в `grade_sheet`;
  - **оценка 3/4/5 не хранится**: она вычисляется из баллов по шкале `score_band`;
  - даты занятий хранятся один раз в семестре (`academic_term`), а не в каждом занятии расписания;
  - организация, где проходит практика, определяется руководителем от организации (`organization_contact`), поэтому в `practice_placement` её нет;
  - причина академа хранится только в `academic_leave`, в приказе — лишь основание (заявление).
- **НФБК** — в каждой таблице любая детерминанта является потенциальным ключом. Альтернативные ключи (`email`, `snils`, `inn`, паспорт в `person`; `code` в `specialty` и `order_type`; `record_book_number` в `student`; `sheet_number` в `grade_sheet`; `inn` в `organization` и т.д.) объявлены как `UNIQUE`.
- Родители вынесены в `contact_person`, а связь со студентом (кем приходится, звонить ли в экстренном случае) — в `student_contact` с ключом «студент + контактное лицо». Иначе у двух братьев один и тот же родитель хранился бы дважды.
- **Осознанное решение: текущее состояние + история.** `student.group_id`, `status_id`, `enrollment_date` и `academic_leave.start_date` — это текущее состояние, а приказы — документы, которые его обосновывают. Формально это не нарушает нормальные формы (внутри таблицы нет зависимостей от неключевых полей) и не выводится однозначно: например, переведённый из другого вуза студент зачислен в свою дату, а не в дату приказа группы. Состояние меняется только исполнением приказа (`fn_apply_due_orders`), прямой `UPDATE` этих полей ролям запрещён.
- **`order_student.applied_at`** — не копия даты вступления в силу, а факт исполнения: приказ может вступить в силу, но ещё не быть исполненным (ежедневный запуск не прошёл, исполнение не удалось), а в один приказ студентов могут включать в разное время. Поэтому он зависит от пары «приказ + студент», а не от приказа.
- **`grade_correction.old_points` / `old_is_absent`** — значения на момент подачи заявки, исторический факт заявки, а не копия текущей оценки (после исполнения текущая оценка равна новой).
- **Шифр группы** хранится, хотя его буквы и год выводятся из учебного плана: это официальный идентификатор, который присваивает вуз (номер группы из плана не выводится). Согласованность шифра с планом гарантирует триггер, поэтому противоречие невозможно.
- `07_fd_scan.sql` ищет по данным всех таблиц пары «A однозначно определяет B». На сгенерированных данных он находит только совпадения генератора: у одной дисциплины одинаковые часы во всех планах, ведомости одного этапа выданы в один день, русские фамилии указывают на пол. Настоящих зависимостей, нарушающих нормальные формы, среди них нет.
- **4НФ и 5НФ** формально тоже выполняются: ни в одной таблице нет двух независимых многозначных фактов, связки M:N бинарные.
- Небольшие технические перечисления (пол, чётность недели, этап и статус ведомости, вид дисциплины) заданы через `CHECK`: у этих значений нет собственных атрибутов, поэтому нормальные формы это не нарушает.

## Ограничения

База рассчитана на курсовой проект и один вуз. Ниже — всё, что в ней сознательно упрощено или не сделано.

### Предметная область
- **Один студент — одна запись на всю жизнь.** `student.person_id` уникален: выпускник бакалавриата, поступающий в магистратуру этого же вуза, или студент на втором высшем не получат вторую запись студента.
- **Один сотрудник — одна должность.** Нет совместительства: преподаватель не может одновременно быть заместителем директора.
- **Курс и номер семестра студента вычисляются по календарю** (с сентября — нечётный семестр), хотя сами семестры есть в `academic_term`. При нестандартном графике это может не совпадать с реальностью. Выпуска нет (тип приказа есть, процедуры нет), поэтому через год ИДБ-23-11 покажется «5 курсом»; выпускников нет и в тестовых данных.
- **Упрощённый учебный план.** Нет часов на контроль, блоков, компетенций, дисциплин по выбору и индивидуальных планов. Перезачёт при переходе в другую группу работает только по совпадению дисциплины и семестра; документов о перезачёте и разницы в планах нет. В тестовых планах нет физкультуры и гуманитарных дисциплин, поэтому у бакалавров около 9 пар в неделю.
- **Шифры групп.** Точно известны буквы И (ИИТ), Д (дневная форма), Б и М (уровень) — по расписаниям и учебным планам СТАНКИНа. Буквы других институтов и заочной формы в справочниках не заданы, и эти позиции шифра не проверяются. Нумерация групп внутри набора (какие номера у какого направления) в тестовых данных условная.
- **Расписание — недельная сетка, развёрнутая в календарь.** Праздники учитываются, но нет разовых переносов и замен пар, отработок перенесённых праздников, дистанционных занятий и расписания сессии (есть только дата экзамена в ведомости).
- **Успеваемость.** Модули и итоговый контроль — в баллах, но итоговый рейтинг по формуле (например, взвешенная сумма модулей и экзамена) не рассчитывается: итоговая оценка — по баллам за экзамен или зачёт. Пересдача на повышение и пересдача аттестованного модуля не поддерживаются; допуск к экзамену по результатам модулей не проверяется.
- **Стипендия хранит только текущую сумму.** При индексации `UPDATE scholarship_type` меняет сумму и для прошлых периодов — истории размеров нет. Право на стипендию по итогам сессии не рассчитывается автоматически.
- **Не реализованы:** приёмная кампания, ГИА как процесс (комиссии, протоколы), дипломы, общежитие (есть только признак «нуждается»), военно-учётный стол (есть только справка), оплата по договорам.
- **Персональные данные — формат РФ.** Паспорт проверяется как 4 + 6 цифр, у иностранных студентов эти поля придётся оставлять пустыми; гражданства нет (только признак «иностранец»); адрес — одной строкой.

### Модель данных
- **Текущее состояние студента** (группа, статус, дата зачисления) хранится рядом с историей приказов. Ролям деканата и агента прямой `UPDATE` этих полей запрещён; владелец БД по-прежнему может изменить их в обход приказа.
- **Приказы на будущее исполняет ежедневный запуск** `fn_apply_due_orders()`. В самой БД планировщика нет: его нужно настроить в бэкенде или через `pg_cron`. Пока запуск не прошёл, вступивший в силу приказ виден в `v_pending_orders`, а статус студента ещё прежний (процедуры для этого студента исполняют его сами).
- **Перевод между институтами одним приказом не поддерживается:** обе группы должны относиться к институту, издавшему приказ. Восстановление в группу другого института возможно (приказ издаёт институт новой группы).
- **Исправление закрытой ведомости** меняет только существующие оценки. Добавить в закрытую ведомость забытого студента нельзя — для него оформляется индивидуальная ведомость.
- **Правила завязаны на названия в справочниках:** «Обучается», «Отчислен», «Бюджет», «Лекция». Если переименовать значение справочника, триггеры и процедуры перестанут его находить. Стабильные коды есть только у типов приказов.
- **Ключ записи в журнале изменений** хранится строкой вида `order_id=6, student_id=13`.
- Сообщения встроенных проверок PostgreSQL (`CHECK`, `UNIQUE`, внешние ключи) — на английском; агенту нужно переводить их для пользователя.

### Безопасность
- **Нет разграничения по строкам (RLS).** Преподаватель может поставить оценку в любую открытую ведомость, агент видит студентов всех институтов. Ограничивать это должно приложение.
- **Кто действовал, в журнал передаёт приложение** (`app.user_id`, `app.agent_request_id`). База ему доверяет: если агент передаст чужой идентификатор, в журнале будет чужое имя. Роль PostgreSQL записывается всегда и подделать её нельзя. По `app.user_id` же определяется, кто подаёт и кто подтверждает исправление оценки, поэтому процедура решения выдана только роли деканата, а не агенту.
- **Владелец БД и суперпользователь могут всё:** отключить триггеры, очистить журнал командой `TRUNCATE`. Защита рассчитана на роли деканата, преподавателя и агента.
- **Паспорта, СНИЛС и ИНН хранятся открытым текстом**, защищены только правами доступа. Для реальной эксплуатации по 152-ФЗ нужны шифрование и другие организационные меры.
- Пароль роли агента в скрипте и хэши паролей пользователей в тестовых данных — заглушки.

### Технические
- **Одновременная работа.** Гонки при параллельных транзакциях исключены для расписания и академических отпусков (рекомендательные блокировки), для запланированных приказов (уникальный индекс: не больше одного на студента) и для заявок на исправление (уникальный индекс и блокировка строки заявки). Остальные проверки в триггерах на уровне изоляции READ COMMITTED теоретически можно обойти двумя одновременными транзакциями; агенту стоит выполнять изменения на уровне `SERIALIZABLE`.
- **Производительность проверена на объёме одного института:** 508 студентов, 25 тысяч оценок, 17 тысяч отметок посещаемости загружаются за несколько секунд со всеми проверками. На масштабе всего вуза (десятки тысяч студентов) не проверялась. Проверка конфликтов расписания и журнал изменений добавляют работу к каждой записи; журнал только растёт, архивации нет.
- **Проверки зависят от текущей даты сервера** (посещаемость не в будущем, возраст, курс, исполнение приказов). Тестовые данные — срез на осень 2026 года; если загрузить их после 08.02.2027, оба запланированных приказа исполнятся при первом запуске `fn_apply_due_orders()`.
- Нет нечёткого поиска по ФИО (например, `pg_trgm`), который пригодился бы агенту для запросов вроде «найди Иванову из ИДБ-23-11».
- Проверено на PostgreSQL 16; нужен PostgreSQL 14+ с расширением `btree_gist`.

## Почему модель дала плохой SQL и текст вместо вызова

Предыдущий запрос109 действительно вызвал `query_deanery` дважды. LM Studio сохранила `finish_reason=tool_calls` и структурированные вызовы. Оба SQL обращались к `student.full_name`, оба получили422 `query_rejected`. В `student` такого столбца нет: имя собрано в `v_students.full_name`. Проверка доступных полей остановила SQL до выполнения. Запрос110 завершился обычным содержимым ответа, `finish_reason=stop`, без `message.tool_calls`, с пустым `tools_used` и без предложения. Напечатанный JSON не исполнялся. [Сохранённое сопоставление provider/canonical](../.local/chat_status_diagnosis/diagnosis-summary.json).

В реально установленном системном сообщении уже есть запрет угадывать столбцы, команда изучать `information_schema.columns`, требование LIMIT и инструкция исправить `query_rejected`. Описание инструмента повторяет эту инструкцию и даёт SQL для получения схемы. [Фактический prompt](../.local/design_polish_backend/deployed-prompt.json), SHA256 `c163aec5de10b7a4c0eded67a9ff38e06a81fb5e50d120f9362542ab667236c2`.

Кешированные метаданные именно Qwen2.5-7B задают формат вызова JSON внутри `<tool_call>...</tool_call>`. [Метаданные](../.local/design_polish_backend/qwen-cached-metadata.json) не являются доказательством активного override-шаблона LM Studio. Фактические структурированные вызовы109 доказывают, что поддержка инструментов в этой связке работает хотя бы для части ответов. Доказательств полного отсутствия tool support, потерянной схемы инструментов или ошибки парсера в запросе110 нет.

У агента последний ответ без структурированных вызовов завершает цикл. `done` означает, что ответ получен и сохранён; это не доказательство выполнения намерения пользователя. Сохраняются только пользовательский текст и конечный ответ ассистента; конкретные ошибки инструментов прежнего запроса не передаются как tool-history в следующем сообщении. Это ограничение восстановления контекста, но его причинное влияние на110 не доказано. Вопрос с вложениями дополнительно ограничивает старую историю целыми парами до6000 UTF-8 байт; для повторного авторизованного чтения файл требуется приложить снова.

Исторические failures вложений сохранены: старая версия вернула JSON `read_attachment_text` как текст; пять длинных файлов дали правильные начала, но выдуманный поздний код без чтения продолжения. Поздний код находится в **первом** файле, фрагмент3: `LATE-91357`. Это ошибки ответа/вызова модели при работающей доставке, а не подтверждение отсутствия данных. [Факты файлов](../.local/design_polish_backend/long-document-truth.json).

Новые backend/prompt/model правки не делались. В оригинальном агенте сохранены14 файлов, совпадающих с ранее независимо проверенным upstream `d92bf5fbfc5b37c3236a6454aeffa5374fe88b11`: [свежая сверка хешей](../.local/design_polish_backend/vendor-hash-check.json). Произвольный JSON из ответа не превращался в исполняемый инструмент.

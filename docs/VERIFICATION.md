# Проверка проекта

Используется предоставленная схема из `sources/deanery_db`: 56 таблиц и 27 представлений. Проверки сосредоточены на предметных процессах, доступе, целостности и настоящих сервисных взаимодействиях.

Проверяем работающие HTTP API, PostgreSQL и реальные службы хранения/очереди. Для изменённого поведения нужны успешный сценарий, существенная граница отказа и отсутствие частичных изменений. Повторять одинаковые DTO для всех таблиц не требуется.

| Группа | Что подтверждает готовность |
|---|---|
| Установка и контракт | Чистая установка новой схемы и учебных данных, исходный SQL smoke, bootstrap администратора, запуск Compose, готовность служб и согласованный OpenAPI. |
| Вход и доступ | Вход/refresh/logout, повтор refresh, отключение пользователя, ограничения попыток; права студента, преподавателя и сотрудников на свои данные, отказ для чужого института, защита персональных данных и журнала. |
| Учебные операции | Зачисление, перевод, отпуск/выход, отчисление/восстановление; новые отложенные приказы и отмена; новый процесс заявки на исправление закрытой оценки с независимым решением и аудитом. |
| Целостность и параллельность | Ошибочная связанная запись отклоняется целиком; повтор команды даёт один результат; конфликтующие операции сохраняют правильное состояние; численность не превышает вместимость. Целевые проверки прежних обнаруженных ошибок сохраняются. |
| Файлы и очередь | Приватные исходные байты, доступ после обработки, карантин вредоносного файла, отказ при недоступном сканере, версия/поиск/экспорт; реальный Linux worker, повтор после остановки без дубликатов. |
| Исходный агент | Настоящий исходный HTTP/SSE сервис, контекст диалога, разрешённое чтение и отказ чужого доступа; просмотр предложения без записи, подтверждение один раз, корреляция запроса и аудита, поиск документов. |
| Итоговый smoke | На одной окончательной сборке: вход → работа с данными → отчёт → загрузка/обработка/скачивание → запрос агента. Повторяем только затронутую регрессию после исправлений. |

На новой схеме выполнены: исходный SQL smoke 184/184; обычные автономные тесты 38; 10 предметных HTTP/SQL сценариев; независимые HTTP smoke 14, проверки сессий 7 и человеческого доступа 6; реальные службы хранения 9; Linux-файлы 7 и остановка/восстановление worker 7. Настоящий исходный агент проверен через HTTP/SSE, включая предложение преподавателя, подтверждение сотрудником и отдельное решение по закрытой оценке. Это отдельные ограниченные наборы, а не оценка всех возможных входов. Итоговая сборка повторно установлена с нуля и запущена; проверены оба шага миграции, создание двух отложенных учебных заданий без дублей, вход из `/docs` и обработка файлов.

Обычная команда `python -m pytest -q` запускает автономные проверки. Предметные проверки `tests/test_core_v2.py` требуют явно заданной синтетической базы `TEST_DATABASE_URL`, адреса `BASE_URL` и тестовых учётных записей; без них они помечаются skipped. Настройки настоящих сервисных сценариев перечислены в началах `tests/test_integration_agent_flow.py`, `tests/test_integration_files_http.py` и `tests/test_integration_recovery.py`. Проверку остановки worker запускайте с единоличным владением тестовой очередью.

Краткий штатный smoke запускается командой из README. Подробные локальные результаты находятся в `.local/test-results`; секреты и токены в них не сохраняются. Сохранены два единичных наблюдения с неустановленной причиной: `401 invalid_token` при первой попытке восстановления и `23514/422` в расширенном сценарии исправления оценки на клоне. Последующие целевые проверки прошли, но не доказывают причины этих сбоев; обходов ошибок в приложение не добавлено.

Локальные детерминированные LLM/BGE подтверждают интеграционный протокол. Качество ответа внешней модели требует настроенного настоящего провайдера и не подменяется таким тестом.
